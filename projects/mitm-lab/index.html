Attack-and-defense security research

A two-person Information Security project at Indiana University Southeast demonstrating how a reverse shell turns a local ARP-spoofing attack into one that can reach past its own network — run entirely on an isolated private network — and the monitoring, firewall, and intrusion-detection work that defends against it.

Why it exists

A course project for Information Security, built with Deecon Precht, on a private lab network we controlled end to end: a victim host, a router, and an attacker host, all on addresses we assigned ourselves. The question was whether a man-in-the-middle attack, which ARP spoofing confines to one local network segment, could be made to reach further — and what would actually catch it if it did.

ARP spoofing works by sending forged Address Resolution Protocol messages that link an attacker's MAC address to another device's IP address, so traffic meant for that device is sent to the attacker instead. It operates at the data-link layer, which is exactly why its reach is normally local: an attacker has to be on the same network segment as the devices it targets.

Extending the attack

A reverse shell inverts the usual connection: instead of an attacker connecting in to a target, the target machine opens an outbound connection back to the attacker. That one inversion is what makes the extension possible, for two reasons. First, outbound connections are what most firewalls are configured to allow, so a reverse shell tends to cross boundaries an inbound connection would not. Second, once that shell is open, the attacker is no longer limited to commands run from their own machine on the local segment — they are running commands as the compromised device, on whatever network segments that device can reach.

That is the actual finding of the project: a device compromised by a reverse shell can be made to carry out ARP spoofing of its own, against other devices on networks it connects to later. The initial, local attack effectively travels with the compromised device rather than staying put. Ettercap did the ARP spoofing and MiTM interception; netcat (via ncat, used over nc for cross-platform compatibility) opened the reverse shell; MSFVenom generated the payload that triggers it. MSFVenom's payloads were not reliable in our testing, which is worth noting on its own — a textbook tool chain does not always behave like the textbook.

We used tcpdump to capture the attack traffic and Wireshark to read it back afterward, which is how the interception was actually verified rather than assumed. The full command sequence — port-forwarding setup, the Ettercap invocation, the listener and payload commands — is in the written report, available on request rather than published inline here, since a copy-paste sequence is a different thing from an explanation of how the technique works.

Detection and prevention

Every attack in this project has a defense documented beside it, because the point was to understand both sides.

Against ARP spoofing: strong, unique device and account passwords; WPA2/WPA3 encryption on Wi-Fi networks; minimizing broadcasted handshake traffic; and restricting port forwarding to what is actually needed, since an open port is an open door regardless of what else is secured.

Against the reverse shell: traffic analysis for unusual outbound connections to unfamiliar hosts or ports; firewall rules that restrict outbound traffic rather than only inbound; endpoint protection that can recognize and block a reverse shell payload before it runs; and an intrusion detection system to flag the pattern even when the payload itself is novel.

Network-wide, the same monitoring and firewall discipline is reinforced by DNSSEC against DNS spoofing, key-based SSH authentication in place of passwords, and routine scanning for the kind of remote-access trojans a reverse shell is a form of. None of these measures requires knowing an attack is coming; they are what makes an attack visible, or impossible, if one does.
